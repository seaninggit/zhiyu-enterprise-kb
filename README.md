# 知域 · 企业知识中台

> 面向企业内部知识生产、审核发布、权限检索、AI 问答与持续治理的一体化知识平台。
>
> 系统以“谁产生、谁维护”为内容责任原则，以三级角色、部门数据隔离、发布门禁和全链路审计保障知识可信；通过 RAG 与知识治理 Agent 提升员工获取知识和管理员治理知识的效率。

[🔗 在线演示](https://zhiyu-kb.xyz)　　[📦 GitHub](https://github.com/seaninggit/zhiyu-enterprise-kb)

---

## 产品定位

企业知识通常分散在文件、制度、流程和人员经验中，常见问题包括版本失控、责任人不清、跨部门越权、搜索无结果、AI 回答无依据以及过期内容长期无人维护。本项目围绕以下闭环建设：

1. 业务部门上传并维护资料，部门管理员审核发布。
2. 用户通过关键词、语义搜索或 AI 问答获取有权限的知识。
3. 用户纠错和 AI 负面反馈进入治理任务，并通知对应负责人。
4. 负责人修订并重新发布后，系统自动关闭反馈并通知原反馈人。
5. 管理员通过规则巡检和 Agent 辅助治理过期、重复、解析失败与知识缺口。

## LLM-Agent 认知深度

### 一、Agent 不是"把工具列表丢给 LLM"

Agent 看起来很简单：定义几个 function，LLM 自动决定调用哪个。实际上线后我发现，**真正的挑战全在边界控制上**。

**我遇到的问题：**

> 给 Agent 配了 7 个知识管理工具后，用户输入"你好"，它仍然调用 `search_knowledge` 检索一遍，然后再回复"你好"。一次简单问候消耗了 2000+ tokens。

**三层护栏：**

```
第一层 · 意图前置分类
  ├─ 7 类非知识意图（身份/能力/寒暄/告别/感谢/确认/账号）
  ├─ 9 类模板 64 条样例 → DashScope 语义向量匹配
  └─ 命中后直接返回模板答案，不进入 Agent/检索流程
        ↓ 未命中
第二层 · 输入特征门控
  ├─ 长度 > 15 字 + 含业务关键词 → 跳过分类，直接检索
  ├─ 长度 ≤ 1 字且无问号 → 引导用户说出需求
  └─ 含"报销/差旅/合同/入职"等词 → 直接检索
        ↓ 进入 Agent
第三层 · 运行约束
  ├─ MAX_ITERATIONS = 5（硬截断，防止循环失控）
  ├─ batch_archive 单次最多 20 篇，且只生成待人工确认的作废建议
  ├─ 工具执行结果截断至 500 字符（避免上下文溢出）
  ├─ 高风险写操作不由 Agent 直接执行
  ├─ 每次工具调用写入审计日志
  └─ 截断时输出已有分析结论，不说"处理超时"
```

**system prompt 是软约束，代码层的护栏才是硬约束。**Agent 行为边界不应该只靠 prompt engineering，需要多层防御架构。**具体来说：工具执行结果必须截断（否则一次 `list_documents` 就能撑爆上下文），写操作必须有人确认（AI 可以建议但不能替人决策），批量操作必须有上限（爆炸半径控制）。

### 二、上下文窗口治理：从"超出限制"到"永不超限"

这是我在这个项目中投入最多思考的产品问题，因为 **LLM 的上下文窗口是所有 AI 产品的隐性天花板**。

**实际遇到过的情况：**

5 轮对话后，每轮检索 5 篇文档（每篇 ~800 字摘要），加上 system prompt 和历史消息，第 6 轮 DeepSeek 直接返回 `context_length_exceeded`。

**这不是靠扩大上下文窗口能解决的问题——模型窗口再大，不控制输入量迟早会爆。我做了四层处理：**

```
Layer 1 · 追问检测
  "那需要什么材料？"  → 检测指代词 "那"，判定为追问
  "报销标准是多少？"   → 检测具体关键词，判定为新问题
  追问时缩小检索范围到上一轮的引用文档，新问题全量检索

Layer 2 · 引用溯源过滤
  LLM 生成答案后正则提取所有 [N] 引用编号
  从 5 篇 source 中只保留实际引用的 2-3 篇
  未引用的检索结果在下一轮中不参与上下文拼接
  效果：后续轮次 context 减少 40-60%

Layer 3 · 滑动窗口裁剪
  检索阶段：全量返回 top-5（保证召回）
  生成阶段：只发送最近 15 条消息（保证不超限）
  system prompt 从 1200 tokens 压缩到 600 tokens

Layer 4 · 会话边界识别
  "好的"、"不需要" → 识别为对 AI 追问的回应，不重新检索
  "再见"、"先这样"  → 识别为会话结束，不发起新检索
```

**上下文管理不是工程优化项，**它决定了你的产品能做几轮对话**。从第 1 天就要设计，否则用户在第 6 轮撞墙时已经失去了信任。

### 三、Token 成本：每个产品决策都有价格

设计过程中逐步意识到：多带一轮历史消息、多传一篇检索结果、system prompt 多写一段话——每个动作都在消耗 Token。成本控制不是研发的优化项，本质上是产品在决定哪些信息值得占用上下文。

**优化前后对比：**

```
优化前（V1.0 初版）：
  每次问答平均消耗 4,500 tokens
  ├─ system prompt:         1,200 tokens（固定开销）
  ├─ 检索结果 context:      2,000 tokens（5篇 × 400字）
  ├─ 历史消息:              800 tokens（最近 4 轮）
  └─ 生成输出:              500 tokens
  日均 200 次问答 × 4,500 tokens = 90 万 tokens/天

优化后（V1.1，即当前版本）：
  每次问答平均消耗 2,200 tokens（↓ 51%）
  ├─ 意图前置识别省掉 30% 请求              ← 短输入直接返回模板
  ├─ system prompt 压缩至 600 tokens        ← 去掉冗余说明
  ├─ 引用后过滤省掉 40% 无关 context        ← 只保留实际引用的文档
  ├─ 上下文追问时检索范围缩小 60%           ← 沿用上一轮文档范围
  └─ 双模型策略：flash 日常 / pro 复杂推理  ← 成本再降 40%
```

| 优化手段 | 类型 | Token 节省 | 需要判断什么 |
|---------|------|-----------|----------|
| 意图前置分类 | 产品策略 | ~30% 请求绕过 LLM | 哪些意图可以不用模型？阈值设多高？ |
| 引用溯源过滤 | 产品策略 | ~20%/轮 | 怎么判断"引用过"？用正则提取 [N] |
| 追问范围收敛 | 交互设计 | ~40% context | 什么是追问？指代词列表怎么维护？|
| 双模型路由 | 成本策略 | ~40% 复杂场景 | flash 和 pro 的切换条件是什么？|
| system prompt 压缩 | 工程优化 | ~10% | 哪些 prompt 内容是模型已知的？|

**如果你在 PRD 里写了"支持多轮对话"，但你不知道第 6 轮会不会因为上下文溢出直接报错——那你写的需求是不完整的。 **AI PM 的需求文档里应该包含 Token 预算**。

### 四、幻觉治理：当 LLM 收到不相关的检索结果

**一个实际例子：**

搜"员工福利标准"，语义向量把"员工手册（含考勤、着装、行为规范）"排到了 top-1。LLM 拿到这份考勤制度后，编了一段"福利包含全勤奖"——这句话在任何企业文档里都不存在。

**针对这个问题，我做了三层处理：**

```
第一道防线 · 检索端
  ├─ 关键词 + 语义双路混合排序（权重 0.28 : 0.42）
  ├─ 标题命中加权（每个关键词命中 +0.06）
  └─ 短语完整命中加分（+0.12）

第二道防线 · 检索后校验
  ├─ 来源相关性检查（areSourcesRelevant）
  ├─ 中文二分词 + 去停用词
  ├─ 标题匹配任一关键词 → 放行
  └─ 否则需要 ≥ 2 个内容关键词命中 → 放行，否则拒答

第三道防线 · 生成后过滤
  ├─ 正则提取答案中的 [N] 引用编号
  ├─ 剔除未被实际引用的 source（避免 UI 误导）
  └─ mode 与 source 矛盾时清空 source 列表（审查一致性）
```

幻觉拒答从"从不拒答"变为该拒就拒，假阳性引用从偶发降为零。

**RAG 不等于"检索到文档→喂给 LLM→输出答案"。**检索到文档只是开始，检索后的过滤和生成后的校验才是质量防线。**

### 五、搜索自学习：让系统从用户行为中自我改进

传统搜索系统的问题是：**用户搜了 A 没结果，换成 B 找到了——这个行为数据被丢弃了**。

我设计了一个自动闭环：

```
用户搜索"差旅费保销" → 0 结果
     ↓ 用户换词
用户搜索"差旅费报销" → 找到 5 篇
     ↓ Cron 定时分析
系统发现: 同用户 24h 内, pinyin 相同, 文字不同
     ↓ 自动创建
search_corrections 表新增: "差旅费保销" → "差旅费报销"
     ↓ 下次命中
下一个用户搜"差旅费保销" → 自动纠错 → 直接找到
```

**几个关键取舍**：

| 决策 | 细节 | 原因 |
|------|------|------|
| 显式规则 vs 算法推断 | 管理员配置的纠错规则优先（置信度 0.99），算法推断为辅（置信度 0.93） | 人工规则宁可少，不能错 |
| 纠错阈值 0.92 | 置信度 ≥ 0.92 才应用纠错 | 低于此值宁可不纠，保留原始查询 |
| 频次下限 = 2 | 候选纠错词必须在本库中出现 ≥ 2 次 | 防止纠到生僻术语 |

**最好的 AI 功能不是"用户输入→AI 输出"，而是**用户用着用着，系统自己变好了**。搜索自学习的投入是一次性的（Cron 脚本），收益是永久的（每个用户受益）。

### 六、检索排序的 IDF 设计：为什么"制度"不能参与排序

关键词匹配的常见陷阱是：**高频官僚词汇污染排序**。

"材料"、"制度"、"管理"、"申请"这些词出现在 80% 的企业文档中，如果每个命中都加同样的分，它们会淹没真正的区分性关键词。

**做法——带噪声惩罚的 IDF 加权：**

```
关键词权重 = token IDF × (term 在 chunk 中出现的文档数 / corpus 总数)

对于低信号词（材料、资料、申请、制度、管理…）：
  → 权重 × 0.15（降权 85%）
  → 它们不再主导排序
```

同时设 `hasStrongMatch` 门控：如果用户查询的区分性关键词在 chunk 中一个都没命中，即使语义相似度很高，得分也上限 0.14——防止"跟问题完全无关但向量撞上了"的假阳性。

**搜索排序的权重调优不是研发调参——**什么词算噪声、噪声的惩罚力度多大，都是产品决策**，需要理解用户实际搜索行为和业务语料特征。

### 七、Agent 工具调用的协议级别细节

Agent 模式下 LLM 返回 tool_calls，系统执行后以 `role: "tool"` 回传结果。这个看似简单的协议在实际落地时有 3 个致命细节：

| 问题 | 现象 | 怎么做 |
|------|------|---------|
| tool_call_id 错乱 | LLM 忽略 tool result，重复调用同一工具 | 严格按 OpenAPI 协议回传原始 id，不乱序 |
| 温度参数不当 | 低温度 tool 调用过于保守，高温度总结胡说 | 分阶段温度：tool-use 阶段 0.2，总结阶段 0.5 |
| 无终止条件 | Agent 连续调用 9 次工具仍未给出终答 | MAX_ITERATIONS = 5，截断时将已有分析作为终答输出 |

**Tool-use 不是"给个 JSON Schema 就完事了"。你需要理解 **LLM 在什么条件下会重复调用、什么时候需要推它一把让它 stop**。这是 PM 的设计职责，不是研发的实现细节。

### 八、从硬编码到语义分类：意图识别的产品演进

**V1.0**：15 条正则表达式硬匹配
- "你是.*" → 身份询问
- "你好.*" → 寒暄
- 覆盖率约 60%，"中午好"、"在吗"、"你叫啥"都匹配不上

**V1.1**：语义向量分类（当前方案）
- 64 条意图模板预计算 1024d DashScope 向量，缓存到 D1
- 用户输入实时向量化（~150ms），余弦相似度匹配最近邻
- 覆盖率 92%，误判率 < 5%

**这个演进路径恰好说明了 AI PM 的核心判断力——**知道什么时候该从规则切换到模型**。规则是精确脆弱的，模型是模糊鲁棒的。选哪个，取决于你的容错率和成本约束。

## 产品功能全景

### 知识全生命周期

```
创建 ──→ 解析 ──→ 审核 ──→ 发布 ──→ 检索 ──→ AI 问答 ──→ 治理 ──→ 审计
  │        │        │        │        │          │          │        │
  │     OCR/切片   驳回     快照    语义+关键词  引用溯源   过期检测   操作记录
  │     PDF/DOCX   退回     版本     权限过滤   多轮对话   重复清理   请求追踪
  │     XLSX/图片  草稿     隔离     纠错建议   办理清单   反馈闭环   敏感操作
  └──────────────────────────────────────────────────────────────────────┘
```

### V2 Agent — 定时自治治理（二期规划）

当前已经具备手动 DeepSeek Tool Calling Agent 和规则型 Cron；以下能力尚未上线，统一纳入二期，不计入当前交付范围：

| 二期能力 | 目标与边界 |
|---------|-----------|
| **定时 Agent 执行器** | Cron 唤醒 Agent，根据目标自主选择扫描与修复工具；支持幂等锁、最大步骤、Token 和费用上限 |
| **解析与索引修复工具** | 增加重新解析、OCR、切片、向量索引工具，仅对低风险失败任务自动重试 |
| **高风险确认中心** | 作废、删除、权限与密级调整必须生成确认单，由管理员批准后执行 |
| **治理 SLA 跟踪** | Agent 检查任务超时、催办负责人并按组织规则升级部门管理员 |
| **Agent 运行实例** | 持久化目标、计划、工具输入输出、耗时、成本、失败重试与终止原因 |
| **效果评测** | 统计发现率、误报率、自动修复率、人工采纳率和单位治理成本 |
| **多 Agent 协作** | 仅在单 Agent 稳定后评估扫描、修复、通知等角色拆分，不作为一期卖点 |
| **企业模型治理** | 建设模型资产目录、生成/向量/OCR 分类、场景路由、评测门禁、灰度发布、成本监控与退役流程；一期仅提供真实服务状态和连接检测 |

二期仍遵循一条边界：审批、权限、状态机、必达通知和审计属于确定性业务规则；Agent 负责理解目标、分析问题和编排工具，不替代业务系统的强约束。

### V1.4 — AI 策略与 PromptOps ✅

管理员可以在后台完成日常回答策略调优，无需修改代码或重新部署应用。

| 功能 | 解决的问题 |
|------|-----------|
| **策略化配置** | 将回答结构、事实约束、语气、详细程度、温度、引用数和输出长度从大段 Prompt 拆成可理解的表单 |
| **自动组装 Prompt** | 管理员配置业务策略，系统自动追加权限、引用和安全约束，减少误删关键护栏 |
| **在线测试** | 选择任意草稿或历史版本，输入真实问题，同时查看模型答案、候选来源和最终组装 Prompt |
| **完整 RAG 评测** | 同一组题真实执行检索和 LLM 生成，联合计算检索命中、答案关键词与引用正确性 |
| **发布质量门禁** | 默认综合得分达到 85 分才能提交审核，未评测和低分版本无法进入生产 |
| **审核发布与回滚** | 强制执行草稿→测试→待审核→生产状态机，保留审核人、时间、评测分和回滚记录 |
| **版本对比** | 两个版本并排查看变更说明、完整指令和生产状态，便于判断调优影响 |
| **运行监控** | 展示近30天问答量、平均响应、引用率、无答案率以及发布/回滚流水 |

日常调优路径：`回答策略 → 保存草稿 → 在线测试 → 运行评测集 → 提交审核 → 审核发布 → 监控 → 必要时回滚`。

后台可以独立调整回答策略和模型生成参数；新增 Rerank、修改权限隔离、接入新模型/OCR/向量库、增加 Agent 工具或改变数据库结构仍属于研发变更。

## 产品经理实战复盘

### 为什么一个 PM 要自己动手

AI 产品的需求边界无法提前完全定义。你没法在 PRD 里写：

> "第 5 轮对话如果上下文超限，系统应智能压缩历史消息并重新检索"

写这行需求的前提是，你得先搞清楚为什么 128K 窗口在第 5 轮就超了。不亲手撞一次 `context_length_exceeded`，根本不知道问题出在哪。

### 踩坑 → 产品优化闭环

| 用户/系统问题 | 根因（LLM 层面） | 怎么做 | 设计逻辑 |
|-------------|-----------------|---------|---------|
| 第 5 轮对话报错 | 上下文溢出，历史消息 + 检索结果超限 | 滑动窗口 + 引用过滤 + 追问检测 | 不依赖模型窗口大小，从产品侧做压缩 |
| AI 基于无关文档编造答案 | 检索假阳性，LLM "努力"基于无关 context 回答 | 来源相关性二次校验 + 拒答 | 检索结果不等于可用证据，需要中间校验层 |
| Agent 疯狂调用工具不停 | 没有迭代上限，LLM 倾向于探索而非收敛 | MAX_ITERATIONS = 5 + 截断输出已有结论 | 模型不会主动停止，需要设计强制终止条件 |
| "我是谁"也要调 LLM 生成 | 所有输入统一走 RAG pipeline | 意图前置分类，非知识意图直接返回模板 | 不是所有输入都值得花 Token，分层路由降本 |
| 同一份文档上传两次标题微调 | 没有上传时重复检测 | 标题相似度实时检查 + 警告提示 | 在用户操作时拦截，比事后清理成本低 |
| 用户搜"报销"命中大量文档 | 关键词匹配无排序 | 标题加权 + 噪声词降权 + 混合排序 | 排序权重反映业务理解，不是纯技术调参 |
| 搜索 0 结果→用户换词→找到 | 搜索行为数据浪费 | 自动建立同音纠错映射 | 用户行为是最好的训练数据，闭环利用 |
| "好的谢谢"触发全量检索 | 短确认被当新问题 | 会话状态感知 + AI 追问识别 | 对话不是独立问答的集合，需要状态机管理 |

### 我的核心收获

**1. AI PM 的核心能力不是会用大模型，是知道它在什么条件下会失败。**

每个功能上线前我问自己三个问题：这个输入最长会多长？如果 LLM 返回了错误格式怎么办？如果用户连续这么用 20 次会不会出问题？

**2. Agent 产品设计，工具定义只占 20%，行为边界占 80%。**

工具定义是 20% 的工作量，剩下 80% 是：什么情况下不调用工具（意图前置）？调用多少次必须停止（硬截断）？工具执行失败后给 LLM 什么信号（错误格式）？

**3. AI 产品的边际成本不在服务器，在 Token。**

AI 产品的边际成本不在服务器，在 Token。每个产品决策——是否多带一轮历史消息、是否加一段 system prompt、是否用更大的模型——都有对应的 Token 代价。

**4. MVP 不是做最少的功能，是找最短的验证闭环。**

我第一版只做了三件事：上传→审核→AI问答。验证这条链路跑通后，再依次加上权限、治理、Agent、决策树。每个迭代都在一个完整闭环上叠加，而不是分散做孤立功能。
